# 清書ルール（YAML → 最終Markdown）

最終Markdownは**チームが見る唯一の成果物**。可読性と肥大化抑制の規則はここに集約されている。
YAMLは足場として捨て、ここから先はMarkdownが正本になる。

## 大原則：肥大化させない

YAMLに構造化したからといって、フィールドを全部散文に展開すると本末転倒で膨らむ。
ここでの仕事は**展開ではなく取捨選択**。

- `importance` を順序と詳しさの両方に効かせる。high は厚く、low は一行か省略。
- 1 concept = 原則1段落。冗長な前置き・締めの定型文（「本ドキュメントでは〜」「以上のように〜」）を書かない。
- `decisions[].over`（棄却案）は決定の理解に不可欠なときだけ一行で触れる。検討の経緯を再現しない。
- `synthesis` を従う：`lead_with` を冒頭に、`foreground` を前面に、`defer_detail`/`terse` は薄く。
- synthesis は入力に過ぎない。「何を強調するか」の指示であって「全部書け」ではない。
- AI臭い水増し（同じことの言い換え、自明な一般論）を入れない。

## 出力構造（既定テンプレート）

対象の性質に応じて柔軟でよいが、既定はこの順序。不要な節は落とす。

```markdown
# {target.title}

## 概要
{1〜3文。この設計が何を、なぜ実現するか。synthesis.lead_with をここで主役にする}

## 背景 / 文脈
{なぜ今これが必要か。前提。必要な場合のみ}

## 設計
{concepts を importance 順に。high は段落、medium は簡潔に、low は必要なら一行}
{relations が複雑なら Mermaid を1つ入れてよい。単純ならグラフより散文}

## 決定事項
{decisions を簡潔に。「{chose} を採用（{because}）」。棄却案は不可欠時のみ}

## リスク
{risks を severity 順に。label・影響・disposition を一行ずつ}

## 未解決事項
{open_questions。blocking のものを先に}
```

## Mermaid の扱い

- relations が3要素以上で絡む、または時系列・依存が重要なときだけ図を入れる。
- 単純な関係を図にしない（散文の方が速い）。図は理解を助けるときだけ。
- 図を入れるなら ```mermaid フェンスで、図と本文の内容を二重化しない（図で示したことを散文で繰り返さない）。

## やってはいけないこと

- YAMLそのものや診断レポートを成果物に貼り付ける（足場は捨てる）。
- `rationale` をそのままコピペする（清書時の文体で書き直す）。
- 全 concept を均等な分量で書く（importance を無視した平板化は肥大化の元）。
- 清書後の最終一読を省く。構造診断は骨格を保証するが、清書LLMの散文は診断が検査していない
  新規出力でレビュー対象外。診断は途中の中間レビューを肩代わりするが、配信前に人間が
  完成物を通し読みする最終レビューは必須の QA ゲートとして必ず残す。
- スキル付属文書（本ルールや診断レポート）の装飾を成果物のスタイル指針と取り違える。
  本ルール散文や診断出力が使う太字は説明上のもので、成果物の必須要素ではない。
  成果物の装飾（太字・強調の有無）はホストの Markdown 規約に従う。

## 例：concept の清書（importance による差）

high の concept:
> RateLimitMiddleware がリクエスト経路の入口でトークンを要求する。ゲートウェイではなく
> アプリ層に置くことで、ルート単位の粒度とテスト容易性を確保している。

low の concept（defer_detail 指定あり）:
> 拒否数は MetricsExporter で出力する。

low を high と同じ厚さで書かないこと。これが肥大化を防ぐ実際の操作。
